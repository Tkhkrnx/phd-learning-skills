# Seven-question research file outputs

Use this reference for a converged, explicitly invoked project research task or when that task requests persistent research files. It adds a delivery format; it does not change evidence search, collaboration, convergence, or Skill activation. Normally, the two research Skills investigate and discuss with the user as already specified in their own workflows, then write the answers that have actually converged. They do **not** require an existing guide or experiment plan as input, and this reference is not a document-migration workflow. Do not create files during early candidate discussion or when the user asks for conversation-only help. Write after the relevant answers have stabilized, or make a user-requested interim snapshot visibly provisional. These are research handoff files, not manuscript prose.

## One writing guide, completed in two passes

Maintain one project writing guide titled `写作指南`. Use the user's target path. If the user asks to revise an existing authoritative guide, update that file in place and preserve its confirmed content. For a new project without a specified path, use `docs/写作指南.md`; if that path or the project's document authority is ambiguous, resolve the target before writing. Validation examples belong in a separate named output directory and must not replace a project's authoritative files.

The purpose of these files is to preserve the *complete working research contract* reached with the user, not to make a short overview. Carry user-confirmed wording, numerical values, RQs, comparison arms, source and split roles, validity rules, figure roles, claim and evidence status, failure/stop criteria, and execution dependencies into the new headings without silently paraphrasing or improving them. The ordinary input is the outcome of the Skills' evidence work and discussion with the user. If a required answer, chapter instruction, figure, or conclusion has not been agreed, mark that slot for discussion rather than composing a plausible replacement. A later explicit request to rewrite prose can reopen this wording boundary.

Only when the user specifically requests reformatting an *existing, already approved* guide and plan—as in a validation example—read those source documents in full and make a source-to-output coverage check. Every decision-bearing paragraph, table, numerical threshold, evidence boundary, baseline-fidelity condition, and artifact rule must either appear in its proper output location or be explicitly identified as transient/history-only. Reorder the agreed text and change Markdown hierarchy as needed; leave genuinely transient run logs and duplicated history in their original files. Do not replace a detailed source section with a one-sentence summary or a link when that section is needed to write, execute, or judge the work. Do not pad the result by attaching the originals verbatim as appendices; integrate the content into the seven questions, writing map, figure/claim map, and executable experiment contract. Give precise source-section provenance and surface source contradictions without silently choosing a new scientific position. This reformatting-only route is **not** the normal way these Skills formulate a new problem or design a method.

Use these seven questions in this order and with these meanings:

1. **问题是什么？** Give the necessary background and a declarative condition or limitation. Keep the objective, cause, challenge, and proposed solution distinct from the problem sentence.
2. **为什么重要？** Explain the consequence and its causal path in the target setting. Use relevant motivation evidence where available; a proposed method's gain is not motivation evidence.
3. **现有工作为什么失败？** Compare the closest work's actual achievements, assumptions, and remaining mismatch with this specific problem. A different method or a limited scope alone is not failure.
4. **核心思想是什么？** Derive the decisive insight from the surviving challenge. State why it could work, its assumptions, and the strongest simpler or competing principle. This may be a system mechanism, benchmark method, measurement principle, or analysis method.
5. **怎么设计？** Explain the minimal end-to-end method, its system or experimental carrier, critical decisions, interactions, costs, and failure handling. Do not substitute a component list for the causal path.
6. **实验计划是什么？** Link each claim to a discriminating research question, fair comparison, relevant metric, evidence unit, and result that could reject or narrow the claim. The separate experiment plan expands execution details.
7. **要得到什么结论？** State the knowledge the study aims to establish and which evidence would justify it. Also state the narrower or contrary conclusion if the decisive evidence disagrees. Before experiments, label conclusions as intended and testable; after experiments, replace them only with source-verified findings and their scope.

The problem-formulation Skill writes Questions 1–3 as paper-quality prose with source and evidence boundaries. It leaves Questions 4–7 explicitly unresolved, rather than drafting a preferred method or result. It may plan a motivation figure or related-work table only when the evidence and comparison are already known. The method-design Skill reads the same guide, preserves confirmed Questions 1–3, and completes Questions 4–7. If new evidence threatens a confirmed earlier answer, expose the conflict and make only the agreed revision. If no guide exists when method design is explicitly asked to produce files, create one from the established problem and mark any unsupported part provisional.

## Writing guide after the seven questions

Add a chapter-by-chapter writing map from **Abstract** through **Conclusion**. For each actual chapter, say what the reader must learn, which of the seven answers it develops, the intended paragraph or argument order, its necessary figures/tables or other evidence, and a wording or claim boundary. Preserve detailed, already-agreed chapter and terminology guidance rather than compressing it to generic chapter names. Adapt the chapters to the contribution and target venue; do not force a new-system paper, a fixed challenge count, or a fixed RQ count. During the first pass, fill the chapters supported by Questions 1–3 and identify dependencies for later chapters without inventing methods, experiments, or outcomes. During the second pass, complete the map.

Include a **figure/table-to-conclusion plan** in the writing guide. Give each necessary figure or table a working label, chapter, primary question or claim, what it must show and compare, the conclusion it would support if the evidence holds, the alternative interpretation if it does not, and its evidence status. A motivation figure supports the problem; a related-work table explains the gap; a design diagram explains the method but does not prove performance; result figures test claims. Several figures may support one conclusion. Do not allocate a figure for every section or fill in favorable numbers before measurement. Keep the wording and figure plan consistent with Question 7.

This project guide is an input to a later explicitly requested systems- or HPC-paper-writing task. It supplies project-specific claims and evidence; the venue writing Skill supplies writing and review guidance. This output format does not invoke or modify those writing Skills.

## Separate experiment plan from method design

When persistent outputs are requested, the method-design Skill also writes a file titled `实验计划`. Use the user's target path or the existing authoritative experiment-plan path when its revision is requested; otherwise use `docs/实验计划.md` in a new project. The writing guide owns the seven-question narrative, chapter map, and planned paper conclusions. The experiment plan expands Question 6 and refers to the guide's claims and figures rather than creating a second research story.

For each decisive experiment, specify the claim/RQ and alternative explanation; evidence unit and data provenance; baseline, treatment, controlled variables and resource fairness; metrics and analysis; validity and failure checks; the planned figure/table; and the result that supports, narrows, or kills the claim. Use matched runs, held-out splits, hardware controls, or formal statistics only where the particular claim requires them. Distinguish proposed, implemented, executed, and verified evidence.

Add an AI-executable sequence: for each next work slice give the verified input or code location to inspect, concrete action, expected artifact, validation, stop/fallback condition, and dependency on preceding evidence. Do not invent commands, owners, paths, permissions, or completed measurements. Keep transient run progress, debugging logs, and raw receipts in the project's existing handoff or artifact system rather than embedding a changing status diary in the scientific plan. Experiment execution itself follows the user's separate authorization and the project's current rules.

## Final consistency check

Check the chain `Questions 1–3 -> 4–5 -> 6 -> 7 -> chapters and figures`. Every planned conclusion needs a discriminating evidence route; every central experiment needs a claim it can affect; every figure needs a reason to exist. Preserve the difference between observed fact, source-backed inference, design hypothesis, planned test, and verified result. Check the current project authority before borrowing an older guide, issue reply, or presentation as an example of format.
